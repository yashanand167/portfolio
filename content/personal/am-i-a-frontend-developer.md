People ask me this more than I expect.

And every time, I pause for just a second too long.

Because the honest answer is not yes. But it is not no either.

## What the label suggests

Frontend developer. The phrase has a shape to it.

It suggests someone who takes a Figma file, translates it into components, hooks up some state, and calls it done. Clean handoff. Clear scope. Ship it.

That is not a bad thing. A lot of great engineers work exactly like that.

But that has never been the full picture of what I do.

## What I actually do

When I sit down with a product problem, I do not start with code.

I start with questions.

What is the user actually trying to do here? Why does this screen exist? Is this the right surface for this information at all?

That instinct is not frontend instinct. That is product instinct. And it shapes every interface decision I make before I write a single line.

## Design engineering is the closest label

The work I do lives at the intersection of design, engineering, and product thinking.

I design interfaces, yes. But I also reason about why they should exist in the first place. I write components, but I also think about what API shape makes the component easiest to use. I care about pixels, but I care just as much about the system behind them.

That is design engineering. It is not a new title. But it finally feels like an honest one.

## The API problem

Here is something that rarely gets talked about.

When you sit close to both design and code, you start caring deeply about the contract between them the API.

Not just the visual API of a component (its props, its variants), but the data API too. What shape should this response be so the UI does not have to do contortions? What should be computed on the server so the frontend can stay clean?

That kind of thinking does not fit neatly into a job description. But it is real work. And it changes the quality of what gets shipped.

## Product thinking is not optional

I used to think product intuition was something that came later, after you got good at code.

I was wrong.

Every interface is a product decision. Every empty state, every loading behaviour, every piece of copy on a button someone had to decide whether that was the right thing to put there. If you are not thinking about that, someone else has to.

I would rather it be me.

## AI is now part of the day

I did not plan for AI to become a daily tool. It just did.

It started with small things generating a rough copy for an empty state, exploring an API I had not worked with before, rubber-ducking a design decision when I was stuck. Gradually it became less of a shortcut and more of a thinking partner.

What I find interesting is that it has not replaced the judgment part. The questions I ask still matter. Knowing whether the output is good still requires the same taste it always did. AI makes me faster. It does not make me less responsible for what gets shipped.

The biggest shift has been in how I explore. I move through unfamiliar territory much quicker now. I can sketch out a component structure, question it, throw it away, and try again without the friction that used to make iteration feel expensive.

That changes how I think at the start of a problem. Less hesitation. More experimentation.

I am still figuring out what that means for craft long-term. But right now, it feels like an honest extension of how I already work curious first, careful second.

## So am I a frontend developer?

Kind of.

I write React. I care about layout and typography. I spend real time thinking about interaction and animation.

But I also design, reason about data models, question product decisions, and think about the experience end to end not just the part I am personally responsible for.

Frontend is where I build.

But it is not the full shape of how I think.

That distinction used to feel uncomfortable to explain. Now it feels like the most accurate thing I can say about myself.
